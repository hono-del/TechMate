## 1. F1 Diagnosis — 入力前は推定を出さない / Keep recommendations empty until input

### フィードバック / Feedback

**English (callout)**

> Before entering any DTCs, failure symptoms, or similar information into the manual diagnosis input area, the “Possible Causes” and “Recommended Diagnostic Flow” fields should remain blank.

**日本語**

手入力欄（DTC・不具合症状など）に何も入れる前は、「推定原因（Possible Causes）」と「推奨診断フロー（Recommended Diagnostic Flow）」を空にする。

**いまのモック / Current mock**

- Manual diagnosis input は空のまま。
- その下の Possible Causes と Recommended Diagnostic Flow は、最初から AI 生成の候補（P0420 前提の触媒／O2／排気漏れ、Check for related DTCs など）が出ている。
- Optional scan は DTC Overview の表示条件に使っているが、推定原因・フローの表示条件には使っていない。

### 修正方針 / Fix policy

1. **入力前は中身を出さない。** Possible Causes と Recommended Diagnostic Flow は、手入力 4 項目（DTC / Failure symptom / Technician findings / Diagnostic result）がすべて空で、Optional scan も未実施のときは空にする。
2. **パネル自体は残す。** レイアウトは崩さない。空のときは「手入力または Optional scan のあとで候補を出す」旨のプレースホルダだけを出す。AI Generated バッジも、候補が出るまで出さない。
3. **表示のきっかけ。** 4 項目のいずれかが 1 文字以上入ったとき、または Optional scan で DTC を取得したときに、いまのモックと同じ候補を出す。Save Input は保存フィードバック用のまま。候補表示の必須条件にはしない。
4. **受付情報だけでは出さない。** 顧客の訴えや受付チェックリストだけでは推定原因・フローを埋めない。診断画面の入力（または Optional scan）が先。
5. **左右の配置は F4。** 候補を出したあとの並びは、フローが左、推定原因が右（次項）。

**やらないこと / Out of scope**

- 入力内容に応じた候補の動的分岐（Q10 の診断側分岐は今回も対象外）。
- 診断機実連携。Optional scan はこれまでどおりモックで P0420 を入れる。

## 1b. F4 Diagnosis — 診断フローを先に出す / Show diagnostic flow first, then possible causes

### フィードバック / Feedback

**English (callout)**

> Once a technician enters a DTC or failure symptom into the manual diagnosis input field, the “Recommended Diagnostic Flow” section should appear first. This allows the technician to perform preliminary checks following the prescribed procedure and only then select the possible cause from the “Possible Causes” list based on their findings. It is unreasonable to ask a technician to select a “Possible Cause” before any preliminary checks have been conducted. Therefore, the “Recommended Diagnostic Flow” section — along with its associated steps — should be moved to the left (the starting point of the process), while the “Possible Causes” section should be positioned on the right.

**日本語**

手入力欄に DTC または不具合症状を入れたら、先に Recommended Diagnostic Flow を出す。手順どおり予備点検してから、所見に基づいて Possible Causes を選ぶ。点検前に原因を選ばせるのは不合理。よってフロー（関連ステップ含む）を左＝工程の起点、推定原因を右に置く。

**いまのモック / Current mock**

- 左が Possible Causes、中央〜右が Recommended Diagnostic Flow とステップ詳細。
- 入力の有無に関係なく、原因カードが先に目に入る。
- Confirm Cause は原因カードの確定が前提。フロー完了は必須ではない。

### 修正方針 / Fix policy

F1（空にする）のあとの並びと読み順。

1. **表示のきっかけは F1 と同じ。** DTC または Failure symptom の入力、あるいは Optional scan のあとでフローと原因を出す。Technician findings / Diagnostic result だけでも出してよい（F1）。ただし「フローが先」の意図に合わせ、DTC / 症状が入ったときを主経路とする。
2. **左をフローにする。** Recommended Diagnostic Flow と、その右隣のステップ詳細（What to Check / Manual / Similar cases）を左側の起点にする。いま左にある Possible Causes を右へ移す。Ask AI for another cause も原因列に残す。
3. **作業順はフロー → 原因。** 整備士は手順で予備点検してから原因カードを選ぶ。入力直後に原因確定を急がせない。Confirm Cause & Create Work Plan は、原因未選択なら押せない（現状維持）。フロー全ステップ完了を CTA 必須にはしない（モックのクリックを増やさない）。
4. **候補の中身は変えない。** フロー 5 ステップと原因 3 枚（触媒 / O2 / 排気漏れ）はいまと同じ。診断側の動的分岐はしない（旧 Q10）。

**やらないこと / Out of scope**

- フロー未完了で原因カードをロックすること（デモが止まるため）。左にフローを置くことで「先に点検」を示す。
- 原因カードの文言・確率ロジックの作り直し。

## 2. F2 Handover — 整備士の UI から外す／操作不可にする / Hide or disable Handover for technicians

### フィードバック / Feedback

**English (callout)**

> Technicians are not responsible for the vehicle handover process following repairs; therefore, this step does not need to appear in the technician’s user interface—or, alternatively, it can be displayed in a grayed-out state.

**日本語**

修理後の車両引渡しは整備士の担当ではない。整備士の画面では Handover ステップを出さなくてよい。出すならグレーアウトでもよい。

**いまのモック / Current mock**

- ステッパーに 6. Handover が常に出る。整備士でもクリックできる。
- 整備士は引渡し画面に入れるが、Complete Job は SA / Admin 専用で押せない。
- 整備士の作業終わりは Work / Explanation Note の Submit for Review。技術完了と顧客引渡しはすでに分けてある。

### 修正方針 / Fix policy

フィードバックは「非表示」と「グレーアウト」の両案。デモでは **工程の全体像を残す** ため、**整備士にはグレーアウト（クリック不可）** を採る。

1. **Technician（山本 健司）**
   - ステッパーの 6. Handover は表示するが、無効・グレー。ツールチップ等で「顧客引渡しは SA / Admin」と出す。
   - `/job/.../handover` を直接開いても入れない。Explanation Note へ戻す。
   - Complete Job は出さない（現状維持）。
2. **Service Advisor / Dealer Administrator / System Administrator**
   - Handover は通常どおり操作できる。引渡しと Complete Job はこれまでどおりこのロール。
3. **Technician Manager（Technician Leader）**
   - フロア整備士（山本）とは別。F5 のとおり、Submit for Review 後は **pending Handover** として開ける。グレーアウトしない。
   - 顧客への車両返却（Complete Job）は SA / Admin のまま。Leader はレビュー依頼の受け取りとノート確認。
4. **番号と工程は変えない。** Reception → Diagnosis → Repair → Check & Verify → Work / Explanation Note → Handover の 6 ステップは残す。Work Planning は出さない（11/13 方針のまま）。

**やらないこと / Out of scope**

- フロア整備士向けに引渡し画面を新しく作ること。
- ロール以外の条件（ノート未提出など）で Handover を消すこと。ノート未提出の制御は現状の CTA のまま。

## 2b. F5 Explanation Note — Submit 後は Technician Leader の Handover 待ちにする / Route Submit for Review to Technician Leader

### フィードバック / Feedback

**English (callout)**

> Once the technician clicks the “Submit for Review” button, the system should automatically route the work order to the account of the corresponding Technician Leader, displaying it as a pending “Handover” task (with prominent highlighting).

**日本語**

整備士が Submit for Review を押したら、対象の Technician Leader のアカウントへ自動回付する。そこでは pending の Handover タスクとして、目立つ強調表示で出す。

**いまのモック / Current mock**

- Submit for Review 後のバナーは「Waiting for SA / Admin」。Technician Leader への回付はない。
- Home に pending Handover キューも、Submit 後の強調表示もない。
- ログインの Technician Leader 相当は **Technician Manager（中村 涼）**。TIE 承認でも Technician Leader と呼んでいる。

### 修正方針 / Fix policy

1. **回付先は Technician Leader。** このモックでは Technician Manager（中村 涼）にマップする。Submit for Review は SA 待ちではなく、まず Leader のキューに入る。
2. **Leader の Home に pending Handover を出す。** 対象ジョブ（RO-2026-10-0042）を Handover 待ちとして表示し、バッジやハイライトで他の In Progress より目立たせる。カードから Handover（説明ノートのレビュー）を開ける。
3. **整備士側の表示を合わせる。** Submitted for review の待ち先を「Technician Leader」にする。ノートの提出は顧客引渡しではない、という文言は残す（F2）。
4. **顧客返却は分けたまま。** Leader がレビューしたあとの Complete Job（車両返却）は SA / Admin。F2 の「フロア整備士は Handover を操作しない」は維持する。
5. **モック範囲。** 実ワークフローエンジンや通知メールは作らない。ログインを中村 涼に切り替えると、強調された pending Handover が見える、で足りる。

**やらないこと / Out of scope**

- 複数 Leader への振り分けルール。
- 実メール / プッシュ通知。

## 3. F3 Check & Verify — 顧客の訴えを最下部の最終確認にする / Move customer concerns to the bottom

### フィードバック / Feedback

**English (callout)**

> Based on the discussion during our meeting last Friday, the “Customer Concerns / Requests” section should be moved to the very bottom of this page to serve as a final confirmation.

**日本語**

金曜の打ち合わせどおり、「顧客の訴え／依頼（Customer concerns / requests）」をこのページの一番下へ移し、最終確認にする。

**いまのモック / Current mock**

- 修理サマリーの直後、Recommended Verification（Post-Repair Checklist 等）より上にある。
- Resolved / Action decided は残っている。Action decided は対応内容の記入が必須。

### 修正方針 / Fix policy

1. **位置だけ変える。** Customer concerns / requests を、技術確認（Recommended Verification・チェックリスト・関連情報）の **下、スティッキーフッターの直前** に移す。
2. **役割は最終確認。** 技術項目を先に潰し、最後に受付内容との突き合わせをする、という読み順にする。見出しやリード文で「技術確認のあと、受付内容を最終確認する」と分かるようにする。
3. **操作ルールは変えない。**
   - 各行は Resolved / Action decided / Pending。
   - Action decided は対応内容（textarea）が必須。未記入なら CTA を押せない。
   - 技術必須項目が残っていても、訴えが Pending でも、Create Work / Explanation Note は押せない。
4. **修理サマリーは上に残す。** 何を直したかの要約はページ先頭のまま。訴えブロックとは別。

**やらないこと / Out of scope**

- 訴えブロックの項目追加・削除。
- Mark All as Passed の復活。

## 5. 確認観点 / What to re-check after the fix

**日本語**

1. 診断を開いた直後、手入力が空なら推定原因と診断フローは空。
2. DTC または症状を入れるか Optional scan すると、左に Recommended Diagnostic Flow（＋ステップ詳細）、右に Possible Causes が出る。
3. 整備士で Handover はグレーで押せない。SA では押せて Complete Job できる。
4. Submit for Review のあと、Technician Manager（Leader）の Home に pending Handover が強調表示される。
5. Check & Verify では技術チェックのあとに顧客の訴えがある。Action decided はメモ必須のまま。

**English**

1. On Diagnosis, Possible Causes and Recommended Diagnostic Flow stay empty until manual input or Optional scan.
2. After DTC / symptom or Optional scan, Recommended Diagnostic Flow (with step details) is on the left; Possible Causes is on the right.
3. Technician sees Handover grayed out and cannot open it. SA can open it and Complete Job.
4. After Submit for Review, Technician Manager (Leader) Home shows a highlighted pending Handover task.
5. On Check & Verify, Customer concerns / requests sit at the bottom. Action decided still requires a written note.
